# UniRig — intégration locale expérimentale (Sprint 3)

**Linux / CUDA, opt-in, inférence non validée.** Le chemin Rigify reste indépendant. Aucun poids, moteur tiers ou installateur n'est livré. Voir [licences, sources et décision](../../docs/etude-backends.md).

## Configuration et UX

1. Sur une machine de test CUDA, préparer un checkout de confiance de [UniRig `6793c664`](https://github.com/VAST-AI-Research/UniRig/tree/6793c6640ff01c8fb389f3993434124bb43d2933) et son environnement Python 3.11 **hors Blender**. Utiliser les dépendances de cette révision (dont PyTorch/CUDA, `bpy` avec OBJ/FBX, PyYAML et les dépendances du module `merge`, notamment Open3D). Épingler les versions et consigner GPU/VRAM et pilote lors du premier essai réel.
2. Fournir manuellement, après revue des droits et de la provenance, les checkpoints squelette et peau dans `experiments/skeleton/articulation-xl_quantization_256/model.ckpt` et `experiments/skin/articulation-xl/model.ckpt` du checkout. Préparer hors du job le **fichier de configuration** `facebook/opt-350m` dans le cache Transformers ; l'amont appelle `AutoConfig.from_pretrained`, puis `AutoModelForCausalLM.from_config`, et n'a pas besoin des poids OPT distincts sur ce chemin. Les checkpoints PyTorch constituent une frontière de confiance : ne jamais charger un fichier inconnu.
3. Dans **AI Rigging — Experimental**, appeler **Experimental UniRig (CUDA)** en mode Objet sur un maillage au repos. Dans le dialogue, renseigner les chemins absolus du Python externe et du checkout. Il n'y a pas de backend de remplacement si CUDA manque. Les chemins ne sont pas enregistrés par le projet.
4. La barre d'état indique l'étape et **Échap** demande l'annulation. Le délai par défaut est de 30 min. Le résultat est une armature de déformation et une copie de maillage ; source, groupes d'origine, sélection et réglages Rigify restent inchangés. Masquer la source pour inspecter la copie superposée et tester la déformation avant usage.
5. **Prepare Smart Pose from Imported Rig** est une étape distincte. Choisir la copie de peau importée et fournir le mapping de repos, par exemple `{"forearm.L":{"head":["nom_os_source","tail"]}}` pour placer le coude gauche à l'extrémité d'un os du rig importé. Les extrémités non mappées gardent le placement initial ; contrôler aussi les rolls. Dans Quick Rigging, générer les contrôles et recalculer les poids CPU sur cette nouvelle copie. Choisir la liaison directe si un GLB SAS est requis. Ce flux ne transfère ni les poids UniRig ni l'animation et ne reconnaît pas automatiquement un humanoïde. La passerelle est testée avec un rig de fixture, pas avec une véritable sortie UniRig.

Le processus sans shell reçoit uniquement le checkout, l'environnement filtré et un dossier temporaire privé contenant la géométrie, sans chemin Godot ni données de projet explicites. L'adaptateur appelle les commandes Python des lanceurs amont (extract → `run.py` squelette → extract → `run.py` peau → merge). Il **n'exécute pas** leurs scripts `bash`, lesquels passent notamment par `eval` et `pip install`. Le `bpy` externe décode le FBX ; Blender ne reçoit que le JSON de réponse. Modes offline HF/Transformers et désactivation W&B : ce n'est **pas** un sandbox OS, utiliser seulement du code de confiance et bloquer le réseau au niveau de l'environnement si une isolation stricte est requise. Les logs temporaires sont supprimés avec le job (dernière ligne bornée remontée sur échec de processus). L'attente d'inférence et la conversion FBX ne bloquent pas le thread UI ; capture et création des datablocks restent synchrones, plafonnées. Après arrêt brutal de Blender ou de l'OS, le nettoyage n'est pas garanti.

## Échange strict `v1`

- UTF-8 JSON, clés exactes, sans doublons, non-finis ni chemins. `request.json` : `schema="sas.rig.request"`, `version=1`, `space="normalized-blender-z-up"`, `mesh_id`, `vertices`, `triangles`. Positions locales centrées et divisées par le demi-plus-grand côté des bounds ; le transform objet reste dans Blender. `mesh_id` : SHA-256 du JSON compact ASCII `[vertices,triangles]` produit par l'encodeur Python, empreinte de corrélation, pas une signature. La requête contient uniquement la géométrie triangulée, pas de matière, UV, scène ni nom du personnage.
- `response.json` : `schema="sas.rig.response"`, mêmes `version`, `space`, `mesh_id`, plus `vertices`, `triangles`, `bones`, `weights`. Les deux tableaux géométriques décrivent le maillage **effectivement** ressorti du FBX et peuvent être réordonnés. Le mapping utilisé pour l'import compare chaque position à une **unique** source (distance ≤ `10⁻⁵` normalisée), exige une bijection et compare le multiensemble des triangles remappés sans tenir compte de leur orientation. Aucun rattrapage par plus proche voisin côté SAS. Le `merge` **amont** fait cependant sa propre estimation d'orientation et son propre transfert ; notre contrôle ne prouve pas la justesse anatomique des poids.
- Chaque os : `name` (unique, UTF-8 ≤ 63 octets), `parent` (`null` pour l'unique racine à l'index 0 ; indice strictement antérieur sinon), `head`, `tail`, `z_axis` (unitaire et orthogonal, pour le roll de repos). Chaque ligne de `weights` correspond au sommet **retourné** du même indice ; 1 à 4 paires `[index_os, poids]` distinctes, poids strictement positifs ≤ 1, somme à `1 ± 10⁻⁵`. Pas de correction silencieuse côté SAS. Maximum 50 000 sommets et triangles, 512 os, JSON ≤ 24 Mio. Maillages avec modificateurs, shape keys, sommets libres, positions ambiguës ou transformations miroir/singulières/cisaillées refusés.
- Blender valide avant mutation, revérifie la géométrie et la transformation de la source avant d'appliquer, remet les poids dans l'ordre source et supprime les nouveaux datablocks si l'import échoue. Les fixtures [requête](fixtures/request.json), [réponse réordonnée](fixtures/response.json) et [processus simulé](fixtures/fake_worker.py) sont synthétiques, sans dépendances ni génération IA.
